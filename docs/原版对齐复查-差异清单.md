## 七、第三批（FolderIconService.cs / MainWindow.xaml.cs）

### 7.1 desktop.ini 的图标路径要纯 ASCII ★ ✅ 已补（本轮，Rust）

原版 `CopyIconToCache` + `GetStableName`：「desktop.ini 中的 IconResource
路径若含非 ASCII 字符，不同编码下极易乱码导致图标加载失败」，
做法是把图标复制进统一副本目录，名取 `SHA1前8位_ASCII净化名`。

本版图标名直接来自用户文件，**中文是常态**。中文名写进 desktop.ini 后
资源管理器可能读不出来，而界面里却显示得好好的（界面走配置里另一条路径）
—— 用户看到的是"同步了但资源管理器没变"，无从下手。

→ 已补 `stable_icon_ref`：非 ASCII 时复制一份到 `icons/_shellcache/`，
desktop.ini 引用副本。**不动** `folder_icons` 登记的原路径 ——
改登记值会让界面里的图标跟着变，那是另一套东西。

哈希用 FNV-1a 而非 SHA1：只用来避重名，不需要密码学强度，
引依赖（动 Cargo.toml）的代价远大于收益。

失败一律退回原路径（不能因为取不到副本就整个功能静默失效）。

> 未覆盖：`mcp.rs` 两处 `apply_icon` 调用暂未接（保守，留待下轮）。

### 7.2 分类标题栏空白处**零延迟**折叠 ★ ✅ 已补（本轮）

原版 `OnGroupBoxHeaderUp`：非文字区"与折叠按钮同速，零延迟"；
只有**文字区**才走 250ms 延迟（区分双击重命名）。

本版 #251 把延迟挂在了名字按钮上（正确），但标题栏**没有可点的空白区** ——
`.fpx-stack-spacer { flex: 0; width: 0 }`，宽度为 0 的元素点不到。
于是整条标题栏只剩 18px 的箭头可点。热区太小是"用起来别扭但说不出哪别扭"。

→ spacer 改为 `flex: 1; min-width: 8px; cursor: pointer`，
并给 head 挂 onClick（`e.target === e.currentTarget` 只认空白区）。

不用 stopPropagation：箭头/名字按钮各有自己的处理，
靠 target 判定比靠阻止冒泡更不容易随结构调整而失效。

### 8.1 剪贴板还要收**图片文件** ★ ✅ 已补（本轮）

原版 `PasteFromClipboard` 有两条分支：

## 九、第六批（MainViewModel.Drag.cs / AgentChain.cs）

### 9.1 移动卡片只从**源页签**摘 ★ ★ ✅ 已补（本轮）

原版 `MoveCardToTabFor` 的注释点明：

> 同路径多页签时按路径 `RemoveAll` 会误删其他页签的同路径卡

本版 `moveCard` 原本是 `for (const t of tabs) t.items = t.items.filter(p => p !== path)`
—— **从所有页签里删**。而同一个路径**可以登记在多个页签**（添加时只查当前页签
有没有重复）。于是拖一次会把它在**其它页签里的登记一并抹掉**，
用户只是在这一页里挪个位置：改了不该改的地方，且没有任何提示。

→ `moveCard` 增加 `fromTabIndex`，只从源页签摘（且只摘找到的第一条：
同一页签内也可能有重复登记）。三个调用点都显式传源。

显式值越界时退回"找第一个含它的页签"，找不到就什么都不做 ——
凭空插入一张不在任何页签里的卡，比不动更糟。

### 9.2 与内置默认逐字一致的模板存 null ★ ✅ 已补（本轮，Rust）

原版 `SetChainTemplate`：「与内置默认一致时存 null 防膨胀」。

不归一化有两个后果：① config 多出一坨与默认重复的文本；
② 更要紧的 —— **那份副本被冻结了**。以后内置默认改进（补占位符、改措辞），
这位用户仍停在旧的那份，而界面上看不出它"不是默认值"，也无从知道该清空。

→ `fpx_save_chain_actions` 保存时比对内置默认，一致则存 null。
**只对内置动作做**：自定义动作没有内置默认，对它比对会把用户恰好写了
同样一句话的模板误删 —— 那是丢数据。

### 10.1 打开备份目录：目录还不存在就**先建** ★ ✅ 已补（本轮，Rust）

原版 `SettingsPanel` 注释：「目录不存在则先创建（备份目录尚未执行过备份时

本版 `fpx_open_backup_dir` 直接 `open_path`，路径不存在就返回「路径不存在」。

### 10.2 内置默认模板要能**取出来** ★ ✅ 已补（本轮，Rust + 前端）

原版 `OnTemplateBoxLostFocus`：「若保存值被规范化（如恢复默认后回读默认文案），
同步回显」—— 清空之后立刻把默认文案显示出来。

### 15.1 保护要下两条 ACE ★★ ✅ 已补（本轮，Rust / Windows 专属，**需实测**）

原版 `Apply` 对每个开关都下**两条** ACE：

| 组 | 作用范围 | 权限 |
|---|---|---|
| `Everyone:(OI)(CI)(…)` | 继承到子文件与子目录 | Delete / WriteRights |
| `Everyone:(…)`（不带继承标记） | **目录自身** | DeleteRights / WriteRights |

· **防删除档**：删除子项的权限检查走的是**父目录**上的 DELETE_CHILD，

· **防写入档**：`CreateFiles` 走父目录的 WriteData 检查，

两种情形都是"用户以为锁住了、实际没锁住"，且**没有任何报错**。

编译不到也跑不到。请本地验证两项：
  1. 受保护目录里删一个子文件 → 应被拒绝（改前是可以删的）；
  2. 解除保护后两条 deny 都被清掉（`/remove:d Everyone` 覆盖全体 deny）。

### 已确认对齐（无需改动）

· 只动「Everyone + Deny + 权限落在管理范围」的 ACE，不碰第三方规则

```csharp
var ownedByThis = CollectLinkNames(key).Where(n => {
    var t = ResolveTarget(LinkPath(key, n));
    return Directory.Exists(t) && Norm(t) == tgp;   // 指向**本次**目标组
}).ToList();
```

本版 #200 写的是"账本里不在本次名单里的**全部**删掉"。

后果：同一项目的不同链接名**可以指向不同的组**（手工建、或从别处迁移过来
就有）。用户这次只是在**乙组**下加/改链接名，而账本里所有没勾的都被删掉 ——
指向**甲组**的那几个会一起消失，**而用户根本没对甲组做过任何操作**。
这类"改了不该改的地方"没有任何报错，用户只会发现别处的链接莫名其妙断了。

→ 三层语义分开（逐名查磁盘实际目标 `resolve_of`）：

| 集合 | 判据 | 用途 |
|---|---|---|
| `to_remove` | 不在名单 **且** 实际指向本组 | 真的删 junction |
| `cancelled` | 不在名单 **且** 未被别组占用（含失效旧名） | 账本剔除的候选 |
| `gone` | `cancelled` ∩（删成功 ∪ 本来失效） | 实际从账本剔除 |

**指向别组的一律保留**（原版 `InspectOwnership` 判定）——
剔掉会让磁盘上仍存在的链接在账本里查不到，变成"静默残骸"（同 #202）。
**删失败的也保留**：账本要写磁盘实际状态。

### 已确认对齐（无需改动）

· **冲突预检**：wanted 里任一名字被普通目录/文件占用则整体阻断
  （防误删内容）→ `junction::create` 的 `LinkState::Conflict` 已覆盖。
· 编辑模式（`assignMode=false`）与分配模式的区分 —— 本版对话框只有一种
  入口语义，未强加。

### 一处断言漏报（本轮修）

分开钉"有 `to_remove`"和"有 `normalize_key(&t) == target_key`"是**漏报**的：
后者在下面的 `cancelled` 里也出现一次，把 `to_remove` 的收窄条件换成
`true` 后断言照样通过。改成钉**连续的一段**才抓得到。

## 二十二、第十九批（FolderCreateService.cs）

### 22.1 创建文件夹必须走摘锁窗口 ★★ ✅ 已补（本轮，Rust）

原版 `FolderCreateService.CreateProject / CreateGroup`：

```csharp
FolderLockService.WithUnlockForPath(full, () => Directory.CreateDirectory(full));
```

`WithUnlockForPath` 从目标路径**逐级向上**找最近的一个受锁祖先并临时摘除。

本版 `sys::create_folder` 直接 `fs::create_dir_all`，没有任何摘锁。

后果：用户给某个目录上了「防写入」后，**在这个目录下新建项目一律失败**
（deny 的 `(OI)(CI)` 会继承到子层级）。而报错只有一句"创建文件夹失败"、
**不含原因** —— 用户不知道是自己刚上的锁挡住了自己，只会以为功能坏了。

这正是"锁"的设计意图：它挡的是第三方（AI 会话进程），
**不是本工具代表用户执行的写入**。所以本工具自己的操作要过窗口。

→ 拆成两步（`resolve_new_target` 算路径 + `create_folder_at` 执行），
`core_create_folder` 在两者之间插 `with_unlock(dir, target)`。
必须先算出目标路径：窗口的 key 就是它，而创建动作又要被窗口包住。

**模板拷贝也在窗口内**（原版整个 `CopyDirectoryRecursive` 都在里面）：
只把建目录包进去的话，受保护目录下建完空目录、接着拷模板会被 ACL 拒绝 ——
用户看到"新建成功但里面是空的"，且没有任何报错。

### 22.2 名称不能以句点结尾 ★ ✅ 已补（本轮，Rust）

原版 `ValidateName` 明写：`if (name.EndsWith(' ') || name.EndsWith('.')) return ...`。

Windows 会**静默**去掉目录名末尾的句点：输入 `foo.` 实际建出 `foo`。
于是配置里存 `foo.`、磁盘上是 `foo` —— 界面照配置显示带句点，
之后所有按名字去查的操作（打开 / 改名 / 删除）都查不到。
**"显示与实际不一致"且没有任何报错**，必须在入口挡掉。

（末尾空格不在此列：本版 `raw.trim()` 已去掉，用户打 `foo ` 得到 `foo`
