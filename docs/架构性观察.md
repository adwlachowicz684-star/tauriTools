## 一、最大的一处：拖拽有四条语义，共用一个内核却各自实现

清单里拖拽相关约 **90 项**（主题索引），分布在 #69-75、#101-111、
#491-495、#695-729 等多处。核对下来发现它们其实是**同一件事的四个变体**：

| 变体 | 落点语义 | 当前实现位置 |
|---|---|---|
| 卡片排序 | 两卡缝隙插竖条，插到第 k 张之前 | `CardGrid` |
| 跨栏建链 | 落在**具体卡片上**，整卡高亮 | `CardGrid` |
| 页签重排 | 越中线判定插入 | `CardGrid`（同一个组件！） |
| 分框重排 | 死区滞后换位 | `StackedGroups`（另起一套） |

**证据**：

- `CardGrid.tsx` 里 36 处拖拽相关代码，**卡片拖拽与页签拖拽写在同一个组件里**，
  注释自己也说"两者落点语义完全不同（一个移动卡片、一个重排页签）"
- `StackedGroups` 的分框重排是**另起的一套**，没有复用
- 清单里 #114（图标排序）、#115（分组排序）还要求第五、第六种变体

**这就是最大的组合空间**：抽一个 `useDragSort` 内核（阈值判定、插入索引、
清理兜底、取消），四个变体各写一个"落点→意图"的适配器。

按现在这个结构，每加一种拖拽就要再复制一遍兜底逻辑 ——
而兜底恰恰是**漏了最难查**的部分（#108 的注释专门写了
"只靠 leave 清理会留下一个待触发的切换，过一会儿页面自己翻了"）。

> 计划里原本就有这条（拖拽 90 项合成 1 个内核 + 4 个适配器），
> 核对下来确认：这个判断是对的，而且现在比当时更值得做（变体还在增加）。

## 四、反复踩的坑，指向同一个根因

这几轮踩的坑列出来看，有明显的共性：

| 坑 | 表象 |
|---|---|
| README 写"MCP 工具 13 个"，实际 24 个 | 手写清单漂移 |
| 色盘两份实现（改一处忘一处） | 复制粘贴 |
| `close_mcp_on_exit` 是死配置项 | 只有字段定义、无读取点 |
| 白名单漏了我新加的 3 条命令 | 加了命令忘了补声明 |
| 越界提示抄成两份，改措辞只改一处 | 复制粘贴 |
| 合并时被上游覆盖我的改动 | 判据错（用 mine≠theirs 而非 mine≠base） |
| 清单"现状"列标「没有」的 #69/#70/#71 实际已有 | 没回代码核 |

**根因都是同一类：同一件事存在两份，或只有一个声明点而没有校验点。**

对应的四种防法，这个仓库**都已经有了**，只是没铺开：

| 防法 | 已有实例 | 该铺到哪 |
|---|---|---|
| 由源码推导，不手写清单 | `known_config_keys()` 序列化推导 | 界面入口清单、白名单 |
| 前后端同数断言 | `cross-end-check.mjs` | 更多对照点 |
| 双向比对脚本 | `scan-invoke.mjs` | 命令注册 vs 白名单 |
| 同步防覆盖自检 | `check-mine.sh` | 已覆盖 12 处 |

**这是我认为最值得投入的一项**：每加一个"声明点"，
就顺手加一条"校验它没漂移"的断言。成本极小，而这七类坑全能被挡住。

## 五、视觉规范可以一次性收口

清单 #276-290（15 项）是"从 NeuTheme 99 个资源"挖出的视觉规范，
加上 #230-237（卡片视觉）、#294-298（派生画刷算法）——
这 20 多项本质是**同一件事**：一套视觉 token + 一个派生函数。

一次做完比逐项做省得多，而且能顺带消灭"同一个概念在不同组件里
写成不同值"的问题（这正是 #454 那类漂移的视觉版）。

## 六、结论：三件事值得优先

| 优先级 | 事项 | 理由 |
|---|---|---|
| **1** | 抽 `useDragSort` 内核 | 拖拽变体还在增加（清单还有第五、第六种），越晚抽越贵 |
| **2** | 铺开"声明 + 校验"的防法 | 七类坑同源，一次性挡住 |
| **3** | 拆 `App.tsx` | 后面还有 ~600 项，现在不拆会到 3000 行 |

第 2 项成本最低、收益最确定，可以先做。
第 1 项要动的东西最多，建议排在拖拽相关功能集中做的时候。
