## 一、TS1261：前提不成立，未做清单建议的改名

清单说同目录下有 `dialogs.tsx`（583 行）与 `Dialogs.tsx`（511 行）两个仅大小写不同的文件。

**本仓库 `components/` 下只有 `dialogs.tsx` 与 `DialogsHub.tsx`** —— 后者是"弹窗调度器"，
前者装五个具体弹窗卡片，**两者名字不同、不存在大小写冲突**。

所以清单建议的"把 `dialogs.tsx` 改名 `dialogCards.tsx`"**没有做**：改名只会在
不存在冲突的前提下制造 churn，还会让远端与本地产生无谓 diff。

已改为加一条**预防性断言**（`type-hygiene-test.mjs`）：一旦真出现两个仅大小写不同的
文件就报错。反向验证过（造一个 `Dialogs.tsx` 会被抓到）。

## 二、TS2304 `setConfirmLink`：已修

`Column` 里引用了 App 的 `setConfirmLink`，props 里没有 → 点链接名那一刻
`ReferenceError`，整块崩。

修法：改为外层传 `onEditLink` prop（现由 `CardGrid` 承接）。

另加了检查器：每个顶层组件块内若出现 `setXxx(` 而该标识符既不在 props 里、
也不在该文件的 useState / const / 导入里声明过，就报错。

## 三、TS18047 `boot` 判空未生效：已修

清单的诊断完全正确：

```ts
const { ctx, boot } = s;              // 解构
if (!selPath || !s.boot) return null; // 判的是 s.boot
boot.config.createProjectDir          // 用的是解构出来的 boot
```

TypeScript 不会把 `s.boot` 的判空窄化传递给已解构的局部变量 `boot`。

现改为清单建议的第 1 种：**不解构**，用局部常量 `const boot = s.boot;`，
判空后全程用它。

（顺带：清单提到 `DialogsHub.tsx` 是 `Dialogs.tsx` 的副本、建议合并 ——
本仓库没有 `Dialogs.tsx`，`DialogsHub.tsx` 是唯一一份，无需合并。）

## 四、TS2339 缺 `card`：**清单建议的修法会掩盖崩溃，已改用另一种**

清单给的方案是"给缺的成员补 `card`，或在使用处先收窄"。

核到源码发现问题**不是类型定义缺字段**，而是 **`??` 与 `?:` 的优先级**：

```ts
selCard?.path ?? dialog.type === 'icons' ? dialog.card.path : ''
```

`??` 优先级高于 `?:`，实际解析成：

```ts
(selCard?.path ?? (dialog.type === 'icons')) ? dialog.card.path : ''
```

**条件变成了路径字符串本身** —— 只要选中了卡片（不管开的是什么弹窗）就为真，
于是去取 `dialog.card.path`，而 `dialog` 多半是 `{ type: 'none' }` → 崩。
默认跟随 + 选中任意卡片 + 没开图标弹窗 = **必崩**。

类型检查只是把它报成"Dialog 上没有 card"。**照清单"补 card"会让崩溃继续存在**，
只是不再报错。真正的修法是**加括号**：

```ts
? (selCard?.path ?? (dialog.type === 'icons' ? dialog.card.path : ''))
```

下一行 `iconTargetName` 一直有这对括号 —— **两行写法不一致本身就是线索**。

## 五、TS2345 类型不匹配：已修，两条路的性质不同

**前三条（string → HotkeyId）**：入口加 `isHotkeyId()` 类型守卫收窄，
不用 `as` 断言。理由与清单一致：拼错的 id 静默取不到键位，界面上只是"没提示"。

**第四条（TabInfo[] → `{ items: string[] }[]`）**：核下来是两个**本就不同**的类型被混用：

| 类型 | `items` | 用途 |
|---|---|---|
| `TabItem` | `string[]` | config.json 里存**路径** |
| `TabInfo` | `CardInfo[]` | 界面用的**卡片详情** |

没有用 `as any` 抹平，而是确保两者各归其位（`Bootstrap.projectTabs` 是 `TabInfo[]`，
`FpxConfig.projectTabs` 是 `TabItem[]`）。

## 为什么用静态断言替代 tsc

沙箱里 `npm install typescript` **装完 node_modules 是空的**（离线环境），
`tsc` 跑不起来。所以把这六类写成 `type-hygiene-test.mjs`（22 项），
**每一条都做了反向验证** —— 把修复回退后断言必须变红。

反向验证记录：

| 回退项 | 是否抓到 |
|---|---|
| 解构 `boot` | ✅ 4 条变红 |
| 去掉 `??` 后的括号 | ✅ |
| 删掉 lock 块的收窄守卫 | ✅ |
| `hint.ts` 去掉 `isHotkeyId` 收窄 | ✅ |
| `onResetLayout?.()` → `()` | ✅ |
| 造一个 `Dialogs.tsx` | ✅ |
| `App.tsx` 出现 `as any` | ✅ |
| `CardGrid` 去掉 `onEditLink` | ✅ |
| 删掉 `setConfirmLink` 的 prop 声明 | ✅ |

### 反向验证中抓到的两个"断言空跑"

1. **`includes('onEditLink')` 会被 `onEditLinkX` 命中** —— 改成 `\bonEditLink\b` 才测得到。
2. **断言指向了不存在的文件** —— 早先写的是 `Column.tsx`（本版没有这个文件），
   `!col || ...` 恒为真，等于没测。改成指向真实存在的 `CardGrid.tsx`。

这两条都属于"断言看着在测、其实没测到"，只有做反向验证才会暴露。
