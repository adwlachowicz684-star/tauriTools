# 应用更新与签名

设置页 →「更新」标签页。GitHub + Gitee 双端点，正式版 / 内部测试双通道。

## 一、四个概念

| 概念 | 是什么 | 在哪 |
|---|---|---|
| **通道** | 正式版 `stable` / 内部测试 `beta`，用户在设置页选，存 localStorage | `plugins/updater/module.js` |
| **endpoint** | 客户端去问"有没有新版本"的 URL，返回 `latest.json` | `src-tauri/src/updater.rs` |
| **latest.json** | 更新清单（版本号 + 各平台的安装包 URL + 签名） | Release 资产 |
| **签名公钥** | minisign 公钥，验安装包签名 | `tauri.conf.json` **和** `updater.rs`（两处必须一致） |

## 二、签名密钥（只做一次，但丢了不可逆）

```bash
npx tauri signer generate --write-keys ~/.tauri/tauri.key
```

输出一把私钥和一把公钥。然后：

1. **公钥**填进 `src-tauri/tauri.conf.json → plugins.updater.pubkey`
2. **同一把公钥**填进 `src-tauri/src/updater.rs → UPDATER_PUBKEY`
   （两处不一致的表现是"某个通道永远验签失败"。`npm run test:updater` 会比对。）
3. **私钥**只留在构建机 / CI secret，**绝不进仓库**

⚠️ **私钥丢了就再也升不了级**：老客户端用旧公钥验不过新签名，且不可逆。

没配公钥时界面会明确显示「尚未配置签名公钥」，不会伪装成"没有更新"。

## 三、发布一个版本

```bash
# 1. 版本号 +1（两处必须一致，脚本会校验，不一致直接拒绝发布）
#    src-tauri/Cargo.toml 的 version（客户端 package_info().version 读的是它）
#    src-tauri/tauri.conf.json 的 version

# 2. 构建并签名（生成 .sig）
export TAURI_SIGNING_PRIVATE_KEY="<私钥内容>"
npm run tauri:build          # Vite 模式
# npm run tauri:build:plain  # 无构建模式

# 3. 一键生成 latest.json 并上传到 Release
export GITHUB_TOKEN=ghp_xxx
npm run release:stable                              # 或 npm run release:beta
#   --notes="..."        更新说明
#   --dry-run            只生成不上传
#   --from-dir=<dir>     用已有产物，跳过构建
```

脚本是 `scripts/publish-update.mjs`。它做四件事：校验版本一致性 →
扫描产物配对「安装包 + .sig」→ 生成 latest.json → 上传到通道对应的 tag。

**四条拒绝发布的硬校验**（都是"发布端看起来成功、客户端静默失败"的类型）：

| 情况 | 不拦的后果 |
|---|---|
| 有 `.sig` 却没有对应安装包 | 清单里出现指向 404 的 url |
| 安装包没有 `.sig` | 每次都能查到更新，安装必失败，错误只说"签名无效" |
| 产物不在白名单（`.dmg`/`.exe`） | 能查到、能下载，但**装不上**，错误只说"解压失败" |
| 一个合法产物都没有 | 生成空 `platforms`，客户端查到更新然后下载 404 |

只认这四种格式：`.nsis.zip` / `.msi`（Windows）、`.app.tar.gz`（macOS）、`.AppImage`（Linux）。

**Release tag 与仓库地址是从 `src/updater.rs` 解析的，脚本里不另存一份。**
两边各写一份、改了一边忘了另一边的下场是：脚本往 A 传、客户端去 B 找，
代码都没错，表现却是"明明发布了，客户端说没更新"，且不报错。
`npm run test:publish-update` 有一条断言把两端钉在一起。

⚠️ **Gitee 镜像需手动同步一份**（`latest.json` + 安装包到
`https://gitee.com/<owner>/tauriTools/releases/<tag>/`）。
Gitee 的 Release 附件接口无法在本环境验证，脚本不做自动上传 ——
传错了不报错比不做更危险。发布完成后脚本会打印需要同步的目标路径。

`latest.json` 结构：

```json
{
  "version": "0.2.0",
  "notes": "更新说明",
  "pub_date": "2026-09-25T10:00:00Z",
  "platforms": {
    "windows-x86_64": { "signature": "<.sig 内容>", "url": "<安装包直链>" },
    "darwin-aarch64": { "...": "..." }
  }
}
```

## 四、端点

`src-tauri/src/updater.rs` 里的两个常量：

```
GH_RELEASE    https://github.com/adwlachowicz684-star/tauriTools/releases/download
GITEE_RELEASE https://gitee.com/REPLACE_GITEE_OWNER/tauriTools/releases/download
```

⚠️ **Gitee 的 owner 要替换成你自己的用户名**，仓库名与 GitHub 保持一致即可。
两个端点按数组顺序**依次尝试**，GitHub 不通时自动回退 Gitee，不需要额外写"选源"逻辑。

## 五、两条容易踩的构建配置

- `bundle.createUpdaterArtifacts` 必须是 `true`。少了它 `tauri build` 不生成 `.sig`，
  表现是"每次检查都能成功、但安装必失败"，而错误只说签名无效，不提示构建期漏了这项。
- `plugins.updater.endpoints` 是**默认流程**用的。本项目的设置页走 Rust 侧按通道覆盖，
  官方文档明确：出于安全原因 endpoints 只能在 Rust 覆盖 —— 所以双通道必须走 Rust。

## 六、为什么 CSP 一个字都不用改

updater 是 **Rust 侧插件**，HTTP 由 Rust 发出，不经过 webview。
`index.html` 那条 `connect-src 'self' ipc: http://ipc.localhost` 保持锁死即可。
（ErgeMD 把 `connect-src` 放开成 `https:` 是它自己的选择，不是 updater 的要求。）

## 七、权限为什么只给内置 updater 插件

三条命令 `updater_check` / `updater_install` / `updater_relaunch` 全是 **M 类**
（见 `js/command-caps.js`）。第三方插件禁 M（`THIRD_DENY_CAPS`）。

更重要的是 **id 必须锁定为内置**：别人若注册一个同名 `updater` 插件，
就能劫持更新通道 —— 这是供应链层面的攻击面，不能靠约定，只能靠 `builtin: true`
（由宿主注入，插件自报无效）。

同理，`capabilities/default.json` **刻意不放**官方的 `plugin:updater|*` 权限：
更新流程只走三条自有命令，不把"下载并安装"直接暴露给 webview。
少了这层收口，任何插件都能触发安装外部二进制。
