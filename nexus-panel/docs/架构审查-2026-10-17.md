## 1. 整体架构

```
┌─ Rust 核心（src-tauri/src/，约 60 条 Tauri 命令）─────────────────┐
│ fpx（项目组）task_board（看板）mcp_gate（MCP 网关）updater        │
│ rt_dep（运行时依赖）dupview（查重）af_flow（agent-flow）           │
├─ 治理层（js/，编译期 + 运行期双闸）───────────────────────────────┤
│ plugin-admit.js（AST 静态准入）  command-caps.js（R/M/W 分级）     │
│ invoke-policy.js（声明+放行双表白名单）  cross-end-check/cmd-scan  │
├─ 前端外壳─────────────────────────────────────────────────────────┤
│ 原生壳 js/shell.js（无构建降级）↔ React 壳 src/App.tsx            │
│ 共用引擎 js/host.js（挂载/桥接/生命周期/服务分发）                 │
│ 插件 SDK js/plugin-sdk.js（module/iframe 双模式同构 ctx）         │
├─ 插件（plugins/，27 个）─────────────────────────────────────────┤
│ app（侧边栏）/ service（被调用）/ toolbar（标题栏）三类            │
│ 挂载：module（同文档）或 iframe（沙箱，runtime-plugins 独立构建）  │
└──────────────────────────────────────────────────────────────────┘
```

**接入关系的核心设计**：插件只依赖 plugin-sdk.js 一个文件；`ctx` 接口在两种挂载模式下完全同构（module 直连 / iframe 走 postMessage 桥接），切换挂载方式不改插件代码。这一条是整个插件体系的承重墙，实测成立。

## 2. 主面板↔插件接入关系（重点）

### 2.1 桥接协议（plugin-sdk.js ↔ host.js）

| 维度 | 实现 | 评价 |
|------|------|------|
| 通道 | `BRIDGE_CHANNEL = 'nexus-bridge-v1'`，request/response 带 seq id | ✅ 版本化通道 |
| 来源校验 | `e.source !== window.parent` 直接丢弃 | ✅ 精确（隔离态下 origin 不可比，窗口引用可比） |
| 超时 | 15s reject，pending 表清理 | ✅ 不会永久悬挂 |
| 失败必回包 | handleBridgeRequest 每个分支都 reply，catch 兜底 | ✅ 「点了没反应」的主要病源已堵 |
| targetOrigin | 宿主 init 时自报 hostOrigin（隔离态插件读不到 parent origin） | ✅ 想得到这一步不容易 |
| 主题推送 | init/theme 消息 + theme-applied 回执 + 400ms 兜底 | ✅ 有确认机制 |

### 2.2 ctx API 面（插件可见的能力全集）

`invoke`（过白名单）/ `services`（服务插件调用，含 available 探测）/ `store`（每插件 KV）/ `fs.claim`（文件归属记账，宿主侧记）/ `on/emit`（事件总线）/ `openArgs/onOpenArgs`（E2 打开参数，两条时序路径都对）/ `openPlugin`（跨插件打开，**宿主侧 builtin 校验**）/ `registerShortcut`（应用级）/ `shortcut`（插件内，激活态限定）/ `addSidebarItem` / `owned`（归属通道）/ `shell.*`（配置/外链/主题/窗口，主平台侧执行）/ `requireDep`（运行时依赖，失败不抛）。

**接入面强度证据**：
- `openPlugin` 的提权防护（借 md 的 fpx_read_file 读任意文件）想到了，且校验放在宿主侧（插件改不动）——注释完整记录了推理链。
- `owned` 通道让「卸载干净」从约定变成结构性保证；同页与 iframe 两侧都发（契约层承诺）。
- module 模式的 invoke 检查是纵深防御（注释自认「不是硬边界」），硬边界在 host.js 桥接侧——定位准确。

**观察项（不修，设计内）**：
- iframe 插件的 SDK 内部 destroy hooks（owned.dispose 等）在宿主侧不可达——宿主只拆文档。SDK 注释里的「ctx.__destroy 排在 iframe.remove() 之前」实际指宿主侧 ctx shim（跑 cleanupFns）。语义上够用（文档销毁即清理），但「插件自己的 onDestroy」对 iframe 插件不生效这一点值得知悉。

### 2.3 生命周期与竞态防护

- `mount` 用 Symbol token 防竞态（切插件快于挂载完成时，晚到的实例被 safeTeardown 拆掉）。
- `safeTeardown` 前后快照差分（auditUnmount，只读不阻断）——残留**可观测**。
- 服务插件懒挂载 + `services` Map 缓存；设置抽屉随 unmount 联动关闭（onSettingsAvailable(false) → closePluginSettings）。
- 文件清单制（fs.claim）：卸载时只报告不自动删（N42：声明的是目录时可能混用户文件，删错不可撤销）。

## 3. 权限体系

### 3.1 三层闸（L1/L2/L3）

```
L1 静态准入（CI 期）  plugin-admit.js：AST 扫 window/document 污染，
                      解构调用绕不过的已列已知局限；deny 拒绝 / review 分诊
L2 命令白名单（运行期）invoke-policy.js：默认拒绝；内置全权；第三方禁 M 类；
                      声明（manifest.commands）+ 放行（用户授权）双表同时满足
L3 沙箱隔离（运行期） iframe sandbox；隔离态（去 allow-same-origin）下
                      一切走桥接，宿主侧执行
```

### 3.2 关键判定复核

| 判定 | 结论 |
|------|------|
| 第三方默认拒绝可绕？ | 绕不过。自定义插件对话框不设 builtin 字段，isTrusted 只认 registry 静态清单；THIRD_DENY_CAPS 按等级禁（新增 M 类自动纳入，不依赖名单维护） |
| 声明+放行双表是否真双查 | 是。且放行记录 revokeAllGrants 在卸载时撤销（本轮补了外链侧的 revokePluginHosts） |
| HARD_DENY 空集 | 查过 8 条无人声明命令后**有意**为空（注释逐条记录理由），保留闸门给将来的「红区」 |
| openPlugin 提权 | 宿主侧 `from?.builtin` 校验，sdk 侧过不了 |
| CSP | `script-src unsafe-inline/eval` 是插件体系的固有代价（运行时加载代码）；`connect-src http://127.0.0.1:* / localhost:*` 放行任意本地端口——本地服务互调的设计内取舍，**远端外传被 default-src 'self' 挡住**；无 CORS 头（MCP 网关同判据）防网页读响应 |
| tauri capabilities | default 能力最小化（窗口控制 + 指定三个 CLI 的 spawn/execute + http 限定 https/本机推理端口） |
| fs 授权（af_fs_allow_root） | **全局共享清单、无按插件归属**。当前只给两个内置插件（agent-flow/settings），第三方被 M 类硬禁 → 不可达。属潜在债：将来若给第三方，需要一个「按插件授权 + 卸载回收」的设计（Rust 侧改） |

### 3.3 权限体系总评

这是同规模项目里少见的完整实现：分级（caps）→ 双表（声明+放行）→ 等级禁（third-deny）→ 沙箱（iframe）→ 静态准入（AST），五层各司其职，注释完整记录每层的「为什么」与「已知局限」。未发现可被利用的缺口。

## 4. 卸载残留（本轮主战场）

### 4.1 残留地图（修复前）

一次「卸载自定义插件」过后，磁盘/存储里剩下什么：

| 残留物 | 存储 | 修复前 | 修复后 |
|--------|------|--------|--------|
| ctx.store 全部 KV | `nexus:<id>:*` localStorage | ❌ 永久残留 | ✅ purgePluginStorage |
| 每插件配置（隔离/主题） | `nexus:plugin-cfg:<id>` | ❌ 永久残留 | ✅ 同上 |
| 外链信任决策 | external-policy hosts（带 pluginId） | ❌ 新插件继承 allow | ✅ revokePluginHosts（打回 pending） |
| 工具栏隐藏/排序/额外入口 | 三张 localStorage 表 | ❌ 失效 id 永久躺底 | ✅ forgetPlugin（两种 id 形态） |
| 命令放行记录 | invoke-grants map | ✅ revokeAllGrants（原有） | 不变 |
| 服务实例（如曾调用过） | services Map + DOM | ❌ 重启前仍可调用 | ✅ dropServiceInstance（拆实例+摘容器+删缓存） |
| MCP 网关代理服务 | 网关注册表 + config.json | ⚠️ 仅设置页 UI 清 | ✅ chokepoint 清（cleanupMcpForPlugin） |
| DOM/快捷键/侧边栏/owned | 内存 + 文档 | ✅ safeTeardown（原有，仅当该插件是激活实例） | 不变 |
| fs 文件账本 | `nexus:fsclaim:<id>` | 刻意不清（N42） | 不变（账本是手工清理依据） |

### 4.2 修复的结构性形状

五路清理全部收口到 **`host.removePlugin(id)` 一处**（返回 `{ok, mcp:{status,error}}`），理由与 owned 通道同族：卸载入口会有多个（设置页、将来的原生壳插件面板），清理放在某个 UI 里就会漏。每路独立 try——一步失败不挡其余步骤，卸载本身必须完成。

关键实现细节：
- **purgePluginStorage 前缀跨文件一致**有测试钉住（uninstall-residue-test 第 3 节）：与 store 写入方（sdk/host 的 `nexus:<id>:`）、plugin-config 的 KEY 逐一比对，漂移即红。
- **forgetPlugin 覆盖两种 id 形态**：工具栏插件记裸 id，应用插件入口记 `tb-entry:<id>`——只删一种会留另一种。
- **dropServiceInstance 先删缓存再拆**：顺序反了的话，拆的过程中一次并发调用会把缓存还魂。
- **MCP 清理失败分开说**：插件已卸是事实，注销失败只说「残留待手动清理」，不把成功报成失败。

### 4.3 测试

`uninstall-residue-test.mjs`（17 项，jsdom + import 真实模块，不手抄实现）：
- forgetPlugin 三表除名/两种形态/落盘复读/不存在 id/空 id
- revokePluginHosts 打回 pending/清 decidedAt/不动别人的/落盘/边界
- 存储前缀跨文件一致（含「刻意不清 fsclaim」的反向断言）

mcp-gate-test 扩展到 102 项：卸载协作断言改为「App.tsx 管 confirm + host.js 管注销」的新分工，并钉住五路收口齐全。
