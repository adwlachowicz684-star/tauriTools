# nexus-panel 架构审查报告

> 2026-10-17 · 审查范围：全工具架构，重点为本轮新建/收尾的 MCP 统一网关（mcp_gate.rs）
> 方法：通读源码（mcp_gate.rs 全文、main.rs 接线、settings 双实现、js 治理层）+ 对照测试体系推断设计意图

## 0. 结论先行

| # | 发现 | 严重度 | 性质 |
|---|------|--------|------|
| A | 设置面板**双份实现**（React App.tsx 1868 行 vs 无构建 index.js 1960 行），每个功能必须写两遍 | 高（成本） | 结构性，测试缓解未消除 |
| B | 无构建版 index.js 是**单文件巨石**（一个 mount() 1960 行），React 版已拆 10 个 Card 组件 | 中 | 架构不对称 |
| C | `slice(i, i + N)` 固定窗口解析源码的模式**三度作案**（本轮修掉 2 处：updater/crossend） | 中 | 模式级风险，无守卫防复发 |
| D | 代理注册存在 **TOCTOU 窗口**（查重名→HTTP 拉取→落库，两步之间可被并发插入） | 低 | 单用户桌面场景可接受 |
| E | `MAX_CONNS` 检查与自增**非原子**，最坏超限 2 个线程 | 低 | 有界，可接受 |
| F | 自动启动失败仅 `eprintln!`，用户侧无感知直到打开设置页 | 低 | 可观测性缺口 |
| G | `mcp_gw_status` 明文回传令牌给前端（设置页要显示） | 低 | 设计内决策（本地工具+仅设置页白名单） |
| H | 代理转发**仅支持 http://、无 chunked、无 keep-alive** | 低 | 明示的范围决策，注释充分 |

**总体判断**：架构质量高于平均水平。红线意识（回环绑定/强制令牌/双下划线命名空间/不静默降级）贯穿且落到注释与测试；治理层（command-caps + invoke-policy + cross-end-check + cmd-scan）是同规模项目里少见的强项。主要欠债是 A/B 的双实现成本，建议排期收敛，不建议在功能期动。

## 1. 整体架构

```
┌─ Rust 核心（src-tauri/src/）──────────────────────────────┐
│ fpx（项目组 26 工具）  task_board（看板 6 工具）            │
│ mcp_gate（统一网关）    updater  rt_dep  dupview  agent-flow│
│         ↕ Tauri 命令层（generate_handler! 约 60 条）        │
├─ 治理层（js/，编译期+运行期双闸）──────────────────────────┤
│ command-caps.js（R/M/W 分级）  invoke-policy.js（插件白名单）│
│ cross-end-check / cmd-scan（源码一致性扫描）                │
├─ 前端外壳（src/ + js/host.js）─────────────────────────────┤
│ React 壳（App.tsx） + 插件 iframe 运行时（runtime-plugins） │
├─ 插件（plugins/，27 个）──────────────────────────────────┤
│ settings（React+无构建双实现）· project-group · task-board │
│ agent-flow · mindmap · md · dupview · …                    │
└────────────────────────────────────────────────────────────┘
```

三个架构决策值得肯定：

1. **命令治理三层闸**：定级（caps）→ 白名单（policy）→ 源码扫描（consistency）。第三方插件默认拿不到 M/W 类命令（`THIRD_DENY_CAPS`），「开监听/改对外连接面」的能力不扩散——这是本地工具的正确安全姿势。
2. **iframe 插件沙箱 + 桥接**：插件跑独立 document，主题/存储经 `ctx.shell` 单向桥接；隔离态（opaque origin）下 localStorage 不可用的问题有系统性认知（多处 try/catch + 降级路径）。
3. **测试即架构**：约 215 个测试脚本 + sweep 元测试（防「崩在半路/恒真断言/零断言」），mcp-gate-test 96 项跨五面（Rust/caps/policy/UI×2）合钉。改动被测试网格兜住的程度罕见地高。

## 2. MCP 网关（本轮主体）架构审查

### 2.1 设计红线（源码注释即规格，全部有测试背书）

| 红线 | 落点 |
|------|------|
| 只绑 127.0.0.1 + 全端点鉴权（含 GET） | `start()` bind + `handle()` 鉴权前置 |
| 工具名强制 `server__tool` 前缀，不猜 | `split_full` 取第一个 `__`；server 名禁含分隔符 |
| 原生直调 / 代理整包转发，不静默降级 | `GatewayTool::invoke`；代理拉不到 tools/list 就不落一条 |
| 令牌重启不变、空令牌启动时生成 | `start()` 生成 + 持久化 |
| 无 CORS 头 | `write_raw` 注释引 fpx P1-8 判据 |

### 2.2 per-server 总开关（本轮新增）——设计正确性核验

- **关闭清单制**（`disabled_servers`）而非开启清单：新注册默认可见，漏配后果从「注册成功但工具不出现」降为「想关的没关」。✅ 正确方向。
- **双过滤**（list 不列 + call 拒绝）：防客户端缓存旧清单后调到一个「未知工具」（而真相是「被关了」）。✅ 覆盖了两种缓存时序。
- **错误文案指路设置**（「已在网关中整体关闭」而非「没有这个工具」）：避免 AI 改调用方式去绕一个面板里的问题。✅ 诊断友好。
- **即时生效与 save_config 分离**：总开关现读 cfg（ Mutex 克隆），不走 needRestart 语义。✅ 命令边界清晰。
- **register/unregister 清理同名记录**：防「关了→移除→重注册→以关态回来」。✅ 闭环。

### 2.3 并发模型

- 每连接一线程 + `MAX_CONNS=32` + 非阻塞 accept + Condvar 唤醒停止。无 tokio/reqwest 依赖——**二进制体积与供应链面的有意取舍**，对本地单客户端场景充分。
- 锁序一致（cfg → tools，无反向嵌套），无死锁路径。 poisoning 全部走 `into_inner()` 降级——正确姿势（本地工具不该因一个 panic 的锁全局瘫痪）。
- `list_tools`/`call_tool` 每次克隆整个 GwConfig：当前 3 字段，无害；若配置长大需改 `Arc<GwConfig>`。

### 2.4 已识别缺陷（按严重度）

**D. 代理注册 TOCTOU**（`register_proxy`）：查重名（解锁）→ HTTP 拉 tools/list（10s 超时窗口）→ 重新加锁插入。并发同名注册会走到插入循环，被逐条 `continue` 挡掉，最终 `n==0` 报「全部重名被跳过」——**失败是干净的，但错误文案误导**（用户会以为对方清单有问题）。建议：插入前再查一次同名服务，直接报「已存在同名服务」。

**E. MAX_CONNS 非原子**：`if live >= MAX { continue }` 与 `fetch_add` 之间两个线程可同时通过 → 最坏 34 个线程。有界无害；要修就 `fetch_add` 后判断再 `fetch_sub`。

**F. 自动启动失败不可见**：setup 里 `Err(e) => eprintln!`。端口被占用时用户完全无感知，直到 AI 客户端连不上、再打开设置页才看到「未启动」。建议：失败时往 state 里记一条 lastError，`mcp_gw_status` 带上，设置页黄条显示。

**H. 代理面收窄是有意的**：http-only / 无 chunked / 无 keep-alive / 无连接池。对端就是本机服务时每项都成立；**若未来要代理远程 MCP server，这三项都要补**（注释已声明 https 明确报错而非降级——这个边界感保持）。

## 3. 结构性欠债（本轮功能之外，但审查范围以内）

### A. 设置面板双实现（高成本）

React 版（App.tsx + 10 个 Card 组件，1868 行）与无构建版（index.js 单文件，1960 行）**功能集成本轮才真正拉齐**（MCP 网关卡之前只在 React 版有——controls-test 抓到并逼出这次补齐）。controls-test 钉「两版页签一致」是对的症状，治的仍是「每个功能写两遍」。

- **短期**：维持现状 + controls-test 守卫（当前策略，有效）。
- **中期**：无构建版按 Card 边界拆文件，至少让「同一功能的两份实现」在两侧都可定位。
- **长期**：评估无构建模式是否还需要独立实现（它是 Vite 构建不可用时的降级路径；若该场景消失，可删除 index.js，一次性消灭整类漂移）。

### B. index.js 巨石（中）

1960 行单 `mount()`，9 个页签全在内。React 版已按 Card 拆分（McpGatewayCard/FilesCard/DepsCard/…），无构建版没有对应结构。功能还在往设置页加（MCP 网关刚加），这个文件会继续长。建议按 A-中期同步拆分。

### C. 固定窗口解析模式（中，模式级）

`src.slice(i, i + N)` 定位代码块的做法在本轮**第三次**造成失败（updater-test +4000、cross-end-check +5000；前两次是历史遗留）。根因：注释增长不可预期地改变偏移量。本轮两处已修为按结构边界（宏结束 `])`）定位。

**建议加守卫**：在 sweep 或 style-audit 里加一条扫描——测试脚本中出现 `slice\(.*\+\s*\d{3,}\)` 且操作对象是 .rs/.ts/.js 源码的，判失败。这是唯一能防止第四、第五次作案的办法。

## 4. 安全面核验（网关相关）

| 面 | 状态 |
|----|------|
| 绑定面 | 仅 127.0.0.1（IPv6 ::1 未覆盖——客户端须用 127.0.0.1，界面显示的 addr 即实际绑定值，无误导） |
| 鉴权 | 全端点强制（含 GET 健康探针）；`constant_time_eq` 防时序侧信道；Bearer/X-Token 双兼容、头名大小写不敏感 |
| 令牌生命周期 | 空则启动时生成（`fpx::safety::random_token`）；持久化；重启不变；前端经 mcp_gw_status 明文可取（仅设置页白名单可达，第三方被 THIRD_DENY_CAPS 挡） |
| CORS | 不设头（防任意网页读 MCP 响应） |
| 请求上限 | body 4 MiB（Content-Length 声明值不直接采信，超限拒）；连接 32 |
| 代理出站 | 仅 http://；令牌经 Bearer + X-Token 双头发给对方（兼容 fpx/task-board 两种风格） |
| 数据目录 | handler 调用时现取（`resolve_data_dir`/`tb_data_dir`）——用户改目录后网关不读旧库；未授权给可操作指引而非兜底默认 |

**未覆盖（可接受）**：无爆破速率限制（本地回环+强令牌，威胁模型不成立）；无 TLS（同前）。
